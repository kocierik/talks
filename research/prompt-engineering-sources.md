# Prompt Engineering Research Ledger

Dated, cited claims for the KCD Provence 2026 talk *Prompt Engineering for
Developers: How to Get Reliable Results from LLMs*. `Keep = yes` rows are
candidates for the slide outline and speaker notes produced in a later task;
`Keep = no` rows were researched and deliberately excluded, with the reason
recorded in Limitation.

`Category` legend: **General LLM practice** = confirmed only against the
supplied Claude reference but not tied to Claude-specific mechanics; **General
practice, cross-vendor** = independently confirmed in two vendors' official
docs; **vendor/model-specific** = the mechanism itself (not just the
underlying idea) is specific to one vendor/model family; **General / Cloud
Native practice** = sourced from a vendor-neutral open project (Kubernetes,
OpenTelemetry).

| Request schema-constrained ("structured") output so calling code can parse it reliably | General practice, cross-vendor | OpenAI, "Structured model outputs" guide; Anthropic, "Structured outputs" (JSON outputs and strict tool use) | 2026-09-15 | OpenAI Responses API (`gpt-4o-mini` and later, `json_schema` strict mode); Anthropic Claude (`output_config.format`, listed supported models) | Not used in the demo; its output contract is natural-language section headers, not an API JSON Schema | Each vendor supports only a constrained subset of JSON Schema (OpenAI requires `additionalProperties:false` and all fields `required`; Anthropic disallows recursive schemas and most numeric/string-length constraints), and schema-conformant output is not the same as factually correct output | no — the demo's output contract is spoken/written language, not an API schema; adding SDK-level schema code would introduce a second vendor's code sample the demoed workflow does not need |
| Give the model callable tools (function/tool calling) instead of asking it to guess facts or actions | General practice, cross-vendor | OpenAI, "Function calling" guide; Anthropic, "Tool use with Claude" overview | 2026-09-15 | OpenAI Responses API (`function_call`/`function_call_output` items); Anthropic Messages API (`tool_use`/`tool_result` blocks) | 60-second extension only — one sentence naming "Tools" (logs, events, metrics, `kubectl`) in Prompt -> Skill -> Tools -> Harness; not demonstrated live, consistent with the no-external-API-dependency constraint | In both vendors' designs the calling application executes the tool and returns the result; the model does not execute code on its own | yes |
| Package reusable domain procedures/expertise as a loadable unit ("Skill") | vendor/model-specific (Claude Agent Skills) | Anthropic, "Agent Skills" overview | 2026-09-15 | Claude API, Claude Code, claude.ai (separately; Skills do not sync across surfaces) | 60-second extension — the "Skill" step, framed as one vendor's name for a broader packaging idea, per the design's vendor-neutral framing | Custom Skills must be uploaded separately per surface, and Anthropic's own guidance treats externally sourced Skills as a code-execution security risk requiring audit | yes |
| Load Skill content in stages: description resident up front, full instructions only once triggered, bundled files only once referenced (progressive disclosure) | vendor/model-specific (Claude Agent Skills) | Anthropic, "Agent Skills" overview — "How Skills work" (Level 1/2/3 loading) | 2026-09-15 | Claude Agent Skills specifically (filesystem- and bash-based loading in Claude's execution environment) | Not spoken in the talk | Depends on Claude's virtual-machine/filesystem/bash architecture; it is not a general prompting technique usable outside that environment | no — real and well-documented, but finer-grained than the 60-second Skill/Tools/Harness summary has room for; naming it would need its own explanation to land |
| An orchestration layer ("harness") coordinates model calls, tool execution, and shared context/state across a multi-step task, and validates tool calls against a schema | General practice, cross-vendor concept (no single named product feature) | OpenAI, "Function calling" guide (the tool-calling flow; strict mode schema validation); Anthropic, "Tool use with Claude" overview (the agentic loop; strict tool use schema validation) | 2026-09-15 | General agentic-system design, demonstrated informally in both vendors' own tool-use documentation (the multi-step request/tool-call/result loop and schema-conformant tool-call validation) | 60-second extension — closing distinction, "a prompt describes the task, a harness controls the work" | The two cited developer guides directly support orchestrating model calls, tool execution, and context/state across turns, plus schema-conformance validation (OpenAI strict mode, Anthropic strict tool use); they do not explicitly document permissions, retries, or stop-condition mechanics as part of a named "harness" layer, so this ledger does not claim vendor-source support for those three elements even though the approved design's own definition of a harness names them. "Harness" itself remains descriptive vocabulary this talk uses for the orchestration layer, not a single standardized artifact or API across vendors | yes |
| The model allocates variable, model-controlled reasoning effort before answering (adaptive/extended thinking) | vendor/model-specific (Claude) | Anthropic, "Prompting best practices" — Thinking and reasoning: Leverage thinking & interleaved thinking capabilities | 2026-09-15 | Claude 4.6+ models (`thinking:{type:"adaptive"}` plus `effort`); earlier models use manual extended thinking with `budget_tokens`, which newer models reject | Not used in the talk | Anthropic's internal evaluations report reliably better performance from adaptive thinking, but the feature's shape has changed across Claude generations (`budget_tokens` is being retired) and does not appear in other vendors' APIs in this form | no — off-thesis; the approved 12-slide outline has no slide on model-internal reasoning controls, and the demo's structured-prompt technique does not depend on a thinking-capable model |
